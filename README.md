# Celestial Lattice Elastic Scatterer

A browser-native computational-physics simulator for deterministic elastic scattering through finite 2D or 3D lattices of spherical scatterers. The trajectory is generated from exact ray-sphere collision geometry and perfectly elastic specular reflection.

> **Research scope:** despite the project name, this first model is not a gravitational celestial-mechanics simulation. It is a fixed-scatterer transport / Lorentz-gas-style model. Gravity, moving bodies, and other celestial-mechanics effects are reserved for later extensions.

## What the simulation solves

The simulator supports two moving-entity models. In **Injected ball** mode, a new projectile sphere starts at the origin. In **Lattice ball** mode, the sphere at the origin is itself the moving lattice entity; it is removed from the static lattice and moves with the same radius as every other lattice sphere. Both modes use initial speed `v` and direction

`v0 = v [cos(theta), sin(theta), 0]`

and travels through a regular 3D cubic lattice with spacing `a`.

The lattice spheres remain fixed. If `Ro` is the lattice-sphere radius and `Rp` is the projectile radius, the projectile-center collision radius is

`R = Ro + Rp`

At collision, with `n` the outward unit normal at the contact point, the velocity is reflected according to

`v_after = v_before - 2 (v_before · n) n`

This conserves speed and kinetic energy up to floating-point error.

The principal observable is the projectile position immediately after the `N`th collision, with `N = 100` as the default target.

## Numerical method

The simulation deliberately avoids brute-force testing of every lattice sphere after every collision.

For each free-flight segment it:

1. Traverses the regular lattice cells using an Amanatides-Woo-style 3D DDA algorithm.
2. Examines only a local `3 × 3 × 3` neighborhood around each traversed cell.
3. Solves ray-sphere intersection analytically for each candidate.
4. Selects the smallest valid positive intersection distance.
5. Computes the exact collision point and surface normal.
6. Applies the elastic reflection equation.
7. Applies a tiny outward numerical nudge to prevent immediate self-recollision from floating-point roundoff.

The lattice is rendered with a single `THREE.InstancedMesh`, avoiding thousands of independent scene objects.

## Complexity

Let `K` be the requested number of collisions and `Ci` the number of grid cells traversed by the `i`th free-flight segment.

### Physics

`O(sum(Ci))`

Each traversed cell performs a constant-size candidate search of at most 27 lattice centers, so the candidate work is `O(1)` per visited cell.

A brute-force implementation would instead approach:

`O(K H^3)`

candidate tests for a lattice half-extent `H`, which becomes unnecessarily expensive as the rendered lattice grows.

### Simulation storage

`O(K)` for recorded collision events and trajectory points.

The collision kernel itself uses constant-size working state apart from those recorded events.

### Rendering storage

The explicit finite lattice requires `O(H^3)` instances for visualization. GPU instancing keeps the draw-call overhead low even though the number of visible spheres still grows cubically.

## Numerical assumptions and limits

- Lattice spacing is exactly `a` in all three dimensions.
- Lattice spheres are fixed.
- Collisions are frictionless and perfectly elastic.
- No gravity, drag, electromagnetic field, or external force is applied.
- The moving particle starts at the origin.
- Injected-ball mode uses a `0.48a` phase shift so the origin is between lattice sites.
- Lattice-ball mode uses lattice sites at integer multiples of `a`, removes the origin sphere from the static lattice, and uses equal moving/static radii.
- The first version uses a cubic lattice only.
- The geometry validator rejects `Ro + Rp >= a/2`, preventing overlapping effective collision envelopes.
- The finite lattice is an approximation to the ideal infinite lattice. A trajectory leaving the finite region is reported as a clean termination.

## Interface

The visualizer provides controls for:

- 2D or 3D visualization mode
- injected-ball or lattice-ball moving-entity mode
- lattice spacing `a`
- obstacle radius
- projectile radius
- projectile speed `v`
- initial angle `theta`
- target collision count `N`
- lattice half-extent `H`
- animation interval

It reports:

- collisions completed
- current/end coordinates `(x, y, z)`
- current speed
- maximum speed-conservation error
- cumulative flight time
- termination status
- a settings record for the exact run
- a collision-history table containing the origin and every reached collision
- CSV export of the recorded settings and collision history

The 3D camera supports orbit and zoom interaction.

## Reproducibility

The simulation is deterministic for a fixed set of parameters and browser floating-point behavior. The path should therefore be reproducible from the same initial conditions, lattice geometry, and collision target.

For research use, record at minimum:

```text
spacing a
obstacle radius Ro
projectile radius Rp
speed v
theta
collision count N
lattice half-extent H
initial lattice phase
```

The geometric path should not depend on `v` in this fixed-scatterer model. Changing speed changes the flight time but not the sequence of geometric reflections, subject to floating-point effects.

## Validation targets

Useful first validation cases include:

- zero or small angle trajectories
- symmetry-related initial conditions
- grazing collisions
- speed-conservation error after many reflections
- comparison against a brute-force reference implementation for small lattices
- convergence checks under smaller numerical nudges and different lattice extents

A future research-grade version should include automated regression tests comparing the accelerated collision kernel against a deliberately simple brute-force solver.

## Planned extensions

The architecture is intentionally separated into physics, simulation state, rendering, and UI so the collision kernel can later move to a Web Worker, WebAssembly, or GPU compute path.

Potential extensions include:

- inverse-square gravity
- moving lattice bodies
- inelastic collisions
- multiple particle species and masses
- thermal velocity distributions
- lattice defects and vacancies
- FCC, BCC and HCP lattices
- electric and magnetic fields
- relativistic corrections
- millions of collision events
- statistical mean-free-path and angular-distribution analysis
- sensitivity / Lyapunov-like trajectory studies
- CSV/JSON trajectory export

## Academic note

The most important conceptual distinction is that the lattice bodies are fixed. Consequently, the collision law is a specular reflection from a rigid spherical boundary rather than the two-body elastic-collision formula used when both masses are free to move.

That distinction should remain explicit in any report or presentation based on this simulator.

## Visualization modes

The interface provides two independent visualization modes:

- **3D mode**: full cubic lattice, with the projectile following the spatial collision trajectory.
- **2D mode**: planar square lattice, with a genuinely two-dimensional collision solver and top-down visualization.

Pressing **Run simulation** starts the projectile at the origin. The camera enters a cinematic follow mode, tracks the projectile through successive free-flight segments, and progressively reveals the trajectory and collision markers. After the target number of collisions is reached, interactive camera controls are restored.

The **Step** control reveals one collision segment at a time without cinematic camera motion.
